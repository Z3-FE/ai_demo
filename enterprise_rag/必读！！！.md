# 企业级 RAG 系统建设总结与架构思路

本文档总结了从零构建一套企业级 RAG (Retrieval-Augmented Generation) 系统的完整过程，涵盖了关键技术决策、遇到的核心问题及解决方案，以及整体架构的设计思路。

---

## 一、 整体架构搭建思路

我们的目标是构建一个可扩展、高性能、具备用户管理能力的 RAG 系统。为此，我们采用了 **前后端分离** + **微服务拆分** 的架构模式。

### 1. 系统拓扑图

```mermaid
graph TD
    Client[React Frontend] -->|HTTP/SSE| Gateway[Business Server]
    Gateway -->|gRPC/HTTP| AI[AI Server]
    AI -->|Read/Write| Milvus[(Milvus Vector DB)]
    AI -->|Read/Write| BM25[(BM25 Index)]
    AI -->|API Call| LLM[LLM Service (OpenAI/Qwen)]
    Gateway -->|Read/Write| SQL[(SQLite/MySQL)]
```

### 2. 核心模块职责

*   **Frontend (React + Tailwind)**: 
    *   负责用户交互（聊天、上传）。
    *   实现流式响应解析（打字机效果）。
    *   管理 Token 鉴权与会话状态。
*   **Business Server (FastAPI)**:
    *   **网关层**：统一入口，负责鉴权 (JWT)、限流。
    *   **业务层**：管理用户、会话历史 (SQLite)。
    *   **代理层**：将 RAG 请求转发给 AI Server。
*   **AI Server (FastAPI + LangChain)**:
    *   **纯计算/推理层**：不关心用户是谁，只关心文档和 Query。
    *   **RAG 引擎**：封装文档切分、向量化、检索、重排序逻辑。
*   **数据存储**:
    *   **Milvus Lite**: 存储向量数据（语义检索）。
    *   **BM25 Index**: 存储倒排索引（关键词检索）。
    *   **SQLite**: 存储用户账号、聊天记录。

## 二、 关键技术点与解决方案

### 1. 混合检索 (Hybrid Search)
单纯的向量检索（Dense Retrieval）容易在专有名词或精确匹配上失分。
*   **方案**：引入 `BM25Retriever` 与 `Milvus` 进行加权融合。
*   **实现**：使用 LangChain 的 `EnsembleRetriever`，权重设为 0.5:0.5。
*   **持久化**：BM25 是内存索引，我们通过 `pickle` 在每次更新时将其序列化到磁盘，服务启动时自动加载。

### 2. 重排序 (Rerank)
检索召回的 Top-K 文档可能包含噪音，直接喂给大模型会降低准确率。
*   **方案**：引入 `DashScope Rerank` (阿里通义千问模型)。
*   **流程**：`Recall (Top 20)` -> `Rerank (Top 3)` -> `LLM`。
*   **效果**：显著提升了上下文的相关性，减少了幻觉。

### 3. 流式响应 (Streaming)
传统的 Request-Response 模式会让用户等待太久。
*   **方案**：全链路 SSE (Server-Sent Events)。
*   **实现**：
    *   AI Server 使用 `langchain.astream` 生成流。
    *   Business Server 使用 `StreamingResponse` 透传流。
    *   Frontend 使用 `fetch` + `ReadableStream` 解析流。

### 4. 依赖与环境管理
*   **uv**: 使用 `uv` 替代 `pip` 进行极速包管理。
*   **版本陷阱**: `langchain` 官方包拆分导致的导入错误，以及 `passlib` 与新版 `bcrypt` 的不兼容问题（通过降级 `bcrypt==4.0.1` 解决）。

## 三、 重要问题 Q&A 总结

### Q1: 为什么要做微服务拆分？
**A**: 将“业务逻辑”（用户、历史）与“AI 能力”（RAG、向量库）解耦。
*   **独立扩展**：AI Server 是 CPU/GPU 密集型，可以单独扩容；Business Server 是 I/O 密集型。
*   **复用性**：AI Server 可以被其他业务线（如客服系统、内部搜索）复用，而不需要关心用户体系。

### Q2: 混合检索里 BM25 的索引怎么保存？
**A**: BM25 默认是内存的。我们实现了一个 `BM25Service`，在每次 `add_documents` 后，将内存中的文档对象序列化为 `bm25_index.pkl` 文件。服务重启时先检查该文件是否存在。

### Q3: Milvus Lite 报错 "File opened by another program"？
**A**: Milvus Lite 基于本地文件，不支持多进程并发写。当 AI Server 正在运行时，无法通过脚本直接操作同一个 DB 文件。解决方案是停掉服务再操作，或者在生产环境使用 Docker 部署标准版 Milvus。

### Q4: 前端报错 "Unexpected className prop"？
**A**: `react-markdown` v9+ 版本移除了 `className` 属性。修复方法是将样式写在包裹 `react-markdown` 的外层 `div` 上，并使用 `@tailwindcss/typography` 插件来美化 Markdown 内容。

### Q5: 注册接口 500 Error (bcrypt 错误)？
**A**: `passlib` 库较老，不支持 `bcrypt` 5.x 版本移除的内部属性。解决方法是降级 `bcrypt` 到 `4.0.1`。

## 四、 快速启动指南

项目根目录下已封装一键启动脚本：

```bash
# 启动所有服务 (AI Server, Business Server, Frontend)
./start_all.sh start

# 重启所有服务
./start_all.sh restart

# 停止所有服务
./start_all.sh stop
```

*   **前端地址**: `http://localhost:5173`
*   **业务接口**: `http://localhost:8000/docs`
*   **AI 接口**: `http://localhost:8001/docs`
